### `f857ec1` in detail (all unverified)

- `CompanionVoiceJobs.swift`: only `ready`/`blocked` jobs count against the 100
  bound (total bound 2000); failed/cancelled generations without a result are
  pruned when a newer generation is created.
- `IOSCompanionSmp.swift`: recording download fails after 60 s without progress
  (total cap 3600 s) instead of a fixed 300 s; resume verifies only the last
  4 KB of the saved prefix.
- `IOSCompanionCoordinator.swift`: snapshots omit `jobs` (Flutter reads job bodies
  through `voiceJob`); GPS runtime state and scan discoveries are in-memory
  (`volatileFields`) instead of journal rewrites; voice inference is deferred on
  `uiBackgrounded`, not on resign-active.
- `CompanionLocationRelay.swift`: `pausesLocationUpdatesAutomatically = false`.

## Test plan on the Mac

Do these in order. Record results in `IOS_COMPANION_DELIVERY.md`.

1. **iOS build.** `flutter build ios --debug` (or Xcode), fix compile errors in
   the four Swift files above first. Then reinstall on the iPhone.
2. **iOS regressions.** Rerun the verified items in `IOS_COMPANION_DELIVERY.md`
   that touch the changed code: recording sync and resume, voice processing,
   GPS relay, scan/selection, Demo Mode.
3. **iOS new behaviour.**
   - Large recording (several MB) download, interrupt it, resume: it completes
     and the resume does not re-read the whole prefix.
   - Pull down Control Center / trigger Face ID during a long transcription:
     inference continues. Sending the app to the background still defers it.
   - Watch requests GPS while the phone is backgrounded and stationary for a
     while: fixes keep arriving.
   - Kill the app while in Demo Mode, relaunch: the watch reconnects.
   - Connect to a watch that never reaches Ready, then the real watch: battery
     and health history keep updating.
4. **Android on the old phone** (no on-device AI expected). Focus on BLE:
   - Normal connect, reconnect after watch reboot, Bluetooth off/on.
   - Recording list with many entries, download, retry.
   - Change time zone / set time manually while notifications are flowing: link
     stays up and the watch clock updates.
   - Burst of notifications plus GPS: no disconnects.
   - If AI cannot run, confirm processing fails cleanly (model missing /
     execution not allowed) and does not block other recordings.

## Android environment on the Mac

Not set up yet. Needed: Android Studio (bundled JDK), Android SDK with the
platform from `android/app/build.gradle.kts`, `adb` on PATH, and
`flutter doctor` clean for Android. `gradlew`, `local.properties` and plugin
registrants are generated by Flutter on the first build; `key.properties` is
only for release signing and is not in Git on purpose.

```bash
cd zswatch_app
flutter pub get
dart run build_runner build --delete-conflicting-outputs
flutter build apk --debug            # also generates android/gradlew
(cd android && ./gradlew :app:testDebugUnitTest)
flutter test
```

Drift tests need a loadable `libsqlite3` (present on macOS by default).

Kotlin unit tests need JDK 21 (LiteRT-LM classes are class version 65). With
Homebrew instead of Android Studio: `openjdk@21`, `android-commandlinetools`,
`flutter config --android-sdk ~/Library/Android/sdk --jdk-dir <jdk21 home>`.

## Known follow-up

Both native journals still rewrite the whole file on each durable change
(Android with fsync). The iOS journal also holds job transcripts and telemetry,
so it can be MBs. Not a correctness bug; the planned fix is to split large,
rarely changing data (recordings, jobs) from high-frequency state into separate
files with an in-place migration.
